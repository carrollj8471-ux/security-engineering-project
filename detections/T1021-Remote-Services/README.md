# Detecting SMB Administrative Share Access with Sysmon and Wazuh

This case study validates detection of Windows administrative-share access and maps the resulting alert to MITRE ATT&CK `T1021.002 – SMB/Windows Admin Shares`.

## Result

A bounded localhost simulation listed `\\localhost\ADMIN$` through SMB without creating, changing, or deleting data. Sysmon recorded the parent PowerShell-to-`cmd.exe` process chain, Wazuh collected it, and custom rule `100190` generated a level 10 alert mapped to T1021.002. A local-directory negative control did not trigger the rule.

| Validation point | Observed result |
|---|---|
| Initial candidate | T1021.006 – Windows Remote Management |
| WinRM result | No listener; configuration left unchanged |
| Final sub-technique | `T1021.002 – SMB/Windows Admin Shares` |
| Simulation | Read-only listing of `\\localhost\ADMIN$` |
| Endpoint telemetry | Sysmon Event ID `1` |
| Detection | Rule `100190`, level `10` |
| ATT&CK tactic | Lateral Movement |
| Negative control | Local `C:\Windows` listing produced no `100190` alert |
| Cleanup | No persistent mapping or test process |

## Objective and hypothesis

The objective was to validate visibility into administrative-share access using an existing Windows remote service without enabling a new listener. The hypothesis was that Sysmon would retain the UNC path in the command line, Wazuh would collect the event, and a child of the active PowerShell-to-command-shell rule could distinguish administrative-share access from ordinary local directory listing.

## Troubleshooting and detection engineering

The first standalone rule did not fire because existing rule `100208` won the event. Converting `100190` into a child of `100208` established the correct hierarchy, but two more live tests still returned no result. Inspection isolated two additional issues: UNC escaping made the original regex unnecessarily brittle, and the custom child was separated from its active parent branch in the XML. The final correction matched the decisive `ADMIN` token and placed `100190` directly beside `100208` and its existing child `100180`.

| Step | Observation | Engineering action | Result |
|---|---|---|---|
| 1 | WinRM had no listener | Preserved the gap; made no configuration changes | Pivoted to existing SMB service |
| 2 | Sysmon event reached Wazuh | Compared archives and alerts | Collection confirmed |
| 3 | Event matched rule `100208` | Converted `100190` to a child of `100208` | Correct branch selected |
| 4 | UNC regex still produced no alert | Reduced the condition to `ADMIN` within the parent context | Escaping uncertainty removed |
| 5 | Child remained separated from parent branch | Moved `100190` next to `100208`/`100180` | Rule fired twice |
| 6 | Local directory control used the same process lineage | Queried for incorrect `100190` results | Negative control passed |

Pre-existing duplicate IDs `100201–100210` and invalid groups affecting rules `100212` and `100214` were observed. They remain separate ruleset-hygiene issues.

### Validated rule hierarchy

```text
Sysmon Event ID 1
└── 100208 — PowerShell launched Windows command shell
    ├── 100180 — netsh interface discovery
    └── 100190 — administrative-share access (T1021.002)
```

### Final rule

```xml
<rule id="100190" level="10">
  <if_sid>100208</if_sid>
  <field name="win.eventdata.commandLine"
         type="pcre2">(?i)ADMIN</field>
  <description>Windows administrative share accessed through a UNC path</description>
  <mitre>
    <id>T1021.002</id>
  </mitre>
  <group>lateral_movement,remote_services,smb_admin_share,</group>
</rule>
```

## False positives and triage

Legitimate administrative-share access may occur during:

- endpoint management and software deployment;
- backup and inventory operations;
- administrator troubleshooting;
- vulnerability scanning and compliance checks;
- incident response and authorized remote support;
- domain administration and maintenance automation.

Analysts should review the destination host, account, source system, parent process, authentication type, share accessed, files touched, execution frequency, and nearby remote-service activity. Higher-risk context includes unusual source hosts, new accounts, remote service creation, copied executables, PsExec artifacts, credential access, or rapid access across multiple systems.

## Engineering considerations

- Extend the rule that wins live evaluation rather than creating a competing standalone rule.
- Keep custom children with their active parent branch where rule order affects evaluation.
- Use Security Events `5140`/`5145` as supporting telemetry when enabled.
- Replace the broad `ADMIN` token with a fully validated UNC/admin-share expression before production deployment.
- Exclude known management systems only with narrow host, account, parent, and maintenance-window conditions.
- Test remote-host access, `C$`, `IPC$`, file copy, service execution, and alternate tools separately.
- Resolve duplicate custom rule IDs to make future parent-child behavior deterministic.

## Findings

### 1. Existing services enabled a safer test

WinRM was unavailable, and the lab did not broaden the attack surface to enable it. The existing SMB service supported a bounded T1021.002 simulation.

### 2. Collection did not equal dedicated detection

The original event was present and promoted as command-shell execution under `100208`, but it lacked the SMB administrative-share classification.

### 3. Parent hierarchy and rule placement were decisive

The successful design extended the active `100208` branch and kept the child beside its parent.

### 4. Negative validation separated context from behavior

The same process lineage did not trigger `100190` when it listed a local path rather than an administrative share.

## Limitations

- The lab used `localhost`, not a second remote Windows host.
- It validated read-only directory listing, not file transfer or remote execution.
- The final regex intentionally matches `ADMIN` broadly inside the `100208` context and requires production hardening.
- Security Event IDs `5140` and `5145` were not the decisive detection source.
- Only one negative-control form was tested.
- Duplicate custom rule IDs remain elsewhere in the manager ruleset.
