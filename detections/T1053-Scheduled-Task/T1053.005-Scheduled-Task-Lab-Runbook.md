# T1053.005 Scheduled Task Detection Lab

## Portfolio objective

Demonstrate how a benign Windows scheduled task generates endpoint telemetry, how Wazuh preserves and evaluates that telemetry, and how a custom detection can distinguish general task creation from a task that launches a command interpreter.

## MITRE ATT&CK mapping

| Field | Value |
|---|---|
| Technique | `T1053.005 – Scheduled Task/Job: Scheduled Task` |
| Tactics | Execution, Persistence, Privilege Escalation |
| Platform | Windows |
| Simulated behavior | Create and run a one-time scheduled task as SYSTEM |
| Primary evidence | Windows Security Event ID 4698 showing task creation and task XML |
| Supporting evidence | Sysmon Event ID 1, task execution, marker-file creation, and Event ID 4699 cleanup |

MITRE documents that adversaries may abuse Windows Task Scheduler for initial or recurring execution, persistence, privilege escalation, or remote execution. This lab maps only the scheduled-task behavior that the evidence directly demonstrates.

References:

- https://attack.mitre.org/techniques/T1053/005/
- https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4698
- https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/audit-other-object-access-events

## Lab environment

- Windows 11 endpoint: `WIN11`
- Domain: `corp.local`
- Sysmon installed and running
- Wazuh agent installed and connected
- Wazuh manager and dashboard available
- Elevated PowerShell or Command Prompt access
- Wazuh archive logging available
- Windows Security log collection enabled

## Safety boundaries

The simulation is local and benign. It does not download content, contact a remote system, modify credentials, disable security controls, or execute an external payload. It creates one scheduled task and one marker file, then removes both during cleanup.

Use this only in the isolated lab. The test creates a task that runs as `SYSTEM`, so elevated privileges are required.

## Detection hypothesis

If an administrator creates a scheduled task, Windows should generate Security Event ID 4698 when **Audit Other Object Access Events** success auditing is enabled. The event should identify the creator, task name, task XML, action, run context, and timestamp.

Wazuh should archive the event and make it searchable. A baseline rule should provide visibility into task creation, while a higher-severity child rule should identify tasks whose XML launches command or scripting interpreters.

## Phase 1: Verify readiness

Run these commands from an elevated PowerShell window on `WIN11`:

```powershell
Get-Service Sysmon, Sysmon64, WazuhSvc, Schedule -ErrorAction SilentlyContinue |
    Select-Object Name, Status, StartType

Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -MaxEvents 3 |
    Select-Object TimeCreated, Id, ProviderName

auditpol.exe /get /subcategory:"Other Object Access Events"

Get-Date -Format o
```

Expected readiness evidence:

- Sysmon, Wazuh, and Task Scheduler services are running.
- Recent Sysmon events are present.
- `Other Object Access Events` success auditing is enabled.
- The timestamp establishes the start of the test window.

If success auditing is disabled, record the original state and enable it in the isolated lab:

```powershell
auditpol.exe /set /subcategory:"Other Object Access Events" /success:enable
```

If Group Policy manages this setting, document that fact rather than repeatedly forcing a local value.

## Phase 2: Create and run the benign scheduled task

Use the same elevated PowerShell window:

```powershell
$TaskName = "T1053.005-Benign-Lab"
$Marker = "C:\ProgramData\T1053.005-scheduled-task-marker.txt"
$StartTime = (Get-Date).AddMinutes(5).ToString("HH:mm")
$TaskCommand = 'cmd.exe /c echo Benign T1053.005 validation %DATE% %TIME% > "C:\ProgramData\T1053.005-scheduled-task-marker.txt"'

Get-Date -Format o

schtasks.exe /Create `
    /TN $TaskName `
    /TR $TaskCommand `
    /SC ONCE `
    /ST $StartTime `
    /RU SYSTEM `
    /RL HIGHEST `
    /F

schtasks.exe /Query /TN $TaskName /V /FO LIST
schtasks.exe /Run /TN $TaskName

Start-Sleep -Seconds 5

Get-Item $Marker | Select-Object FullName, Length, CreationTimeUtc, LastWriteTimeUtc
Get-Content $Marker
Get-FileHash -Algorithm SHA256 $Marker

Get-Date -Format o
```

Do not rerun the task-creation command until the first Event ID 4698 has been located. A single creation produces a cleaner evidence timeline.

## Phase 3: Confirm local Windows telemetry

### Security Event ID 4698

```powershell
$Start = (Get-Date).AddMinutes(-20)

$CreatedTaskEvent = Get-WinEvent -FilterHashtable @{
    LogName   = "Security"
    Id        = 4698
    StartTime = $Start
} | Where-Object {
    $_.Message -match "T1053\.005-Benign-Lab"
} | Select-Object -First 1

$CreatedTaskEvent |
    Format-List TimeCreated, Id, RecordId, ProviderName, Message
```

Capture the creator account, domain, logon ID, task name, task content, action, run account, client process ID, parent process ID, and timestamp.

### Sysmon supporting evidence

```powershell
Get-WinEvent -FilterHashtable @{
    LogName   = "Microsoft-Windows-Sysmon/Operational"
    Id        = 1
    StartTime = $Start
} | Where-Object {
    $_.Message -match "schtasks\.exe|T1053\.005-scheduled-task-marker"
} | Select-Object -First 10 TimeCreated, Id, Message
```

Do not assume the scheduled action's parent process. Record the actual parent shown by Sysmon.

## Phase 5: Add ATT&CK-mapped Wazuh rules

On the Wazuh manager, confirm that IDs `100120` and `100121` are unused:

```bash
sudo grep -R -n --include='*.xml' -E 'id="(100120|100121)"' \
/var/ossec/etc/rules /var/ossec/ruleset/rules
```

If either ID exists, stop and select unused IDs from Wazuh's custom-rule range.

Back up and edit the local rules:

```bash
sudo cp /var/ossec/etc/rules/local_rules.xml \
/var/ossec/etc/rules/local_rules.xml.bak-t1053-005

sudo nano /var/ossec/etc/rules/local_rules.xml
```

Append:

```xml
<group name="windows,scheduled_task,mitre,">

  <rule id="100120" level="5">
    <decoded_as>windows_eventchannel</decoded_as>
    <field name="win.system.providerName"
           type="pcre2">(?i)^Microsoft-Windows-Security-Auditing$</field>
    <field name="win.system.eventID">^4698$</field>
    <description>Scheduled task created: $(win.eventdata.taskName)</description>
    <mitre>
      <id>T1053.005</id>
    </mitre>
  </rule>

  <rule id="100121" level="8">
    <if_sid>100120</if_sid>
    <field name="win.eventdata.taskContent"
           type="pcre2">(?i)(cmd\.exe|powershell\.exe|pwsh\.exe|wscript\.exe|cscript\.exe)</field>
    <description>Scheduled task created with command or script interpreter</description>
    <mitre>
      <id>T1053.005</id>
    </mitre>
  </rule>

</group>
```

Rule `100120` establishes task-creation visibility. Rule `100121` raises severity when the task XML contains a command or scripting interpreter. Interpreter use is suspicious context, not proof of maliciousness.

Validate the rules before restarting:

```bash
sudo /var/ossec/bin/wazuh-logtest
```

If the rules load without an error, exit with `Ctrl+C` and run:

```bash
sudo systemctl restart wazuh-manager
sudo systemctl is-active wazuh-manager
```

Do not proceed unless the manager returns `active`.

## Phase 7: Benign negative control

The negative control creates a task with a direct native executable instead of a command or scripting interpreter. It should trigger baseline rule `100120` but not higher-severity rule `100121`.

Run from elevated PowerShell:

```powershell
$ControlTask = "T1053.005-Benign-Control"
$ControlTime = (Get-Date).AddMinutes(5).ToString("HH:mm")

schtasks.exe /Create `
    /TN $ControlTask `
    /TR "C:\Windows\System32\hostname.exe" `
    /SC ONCE `
    /ST $ControlTime `
    /RU SYSTEM `
    /RL HIGHEST `
    /F
```

Validate:

```text
agent.name:"WIN11" AND rule.id:"100120" AND data.win.eventdata.taskName:*T1053.005-Benign-Control*
```

Expected: one baseline task-creation alert.

```text
agent.name:"WIN11" AND rule.id:"100121" AND data.win.eventdata.taskName:*T1053.005-Benign-Control*
```

Expected: zero higher-severity interpreter alerts.

## Phase 8: Cleanup and deletion evidence

Run from elevated PowerShell:

```powershell
schtasks.exe /Delete /TN "T1053.005-Benign-Lab" /F
schtasks.exe /Delete /TN "T1053.005-Benign-Control" /F

Remove-Item "C:\ProgramData\T1053.005-scheduled-task-marker.txt" \
    -Force -ErrorAction SilentlyContinue

Get-Date -Format o
```

Confirm the tasks are gone:

```powershell
schtasks.exe /Query /TN "T1053.005-Benign-Lab"
schtasks.exe /Query /TN "T1053.005-Benign-Control"
```

Expected: both queries report that the specified task does not exist.

Hunt for task deletion:

```text
agent.name:"WIN11" AND data.win.system.eventID:"4699" AND data.win.eventdata.taskName:*T1053.005*
```

## Detection engineering analysis

Scheduled tasks are common in legitimate administration, software updates, monitoring, backup operations, and endpoint management. Task creation should not automatically be treated as malicious.

Detection fidelity improves when analysts consider:

- task location and naming pattern;
- creator account and logon context;
- action executable and arguments;
- use of command or scripting interpreters;
- SYSTEM or other privileged run contexts;
- hidden settings or password-based logon types;
- unusual triggers, repetition, or execution times;
- creation on critical systems;
- nearby remote logons, file writes, downloads, or credential access.
